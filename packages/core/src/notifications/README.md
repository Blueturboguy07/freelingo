# Notification planning boundary

`buildNotificationPlan` computes a complete desired set from injected durable facts. It has no network, timers, native imports, writes or permission requests. `chooseTemplate` exposes the same per-course eligibility and ordered arbitration for audit. `notificationMayPresent` rechecks a generated payload against a fresh snapshot before presentation.

The host provides one clock context: `nowUtc`, IANA `timeZone`, actual `localDay`, actual next local-day boundary, and the account-day facts. Goal attainment and streak extension are distinct. Per-course mistakes, recent weak items and content availability come from installed pack/SQLite data. A stale day produces no requests. The caller must not reuse yesterday's day facts to construct tomorrow's state.

Daily occurrences contain both civil calendar fields and the UTC instant computed by the platform clock adapter. The planner verifies that they join in the current zone and match the saved reminder time. The rolling window is seven civil days; past times are omitted. Do not manufacture a fixed UTC offset across DST. If a chosen wall time does not occur on a calendar day, omit that occurrence instead of backfilling it immediately. Daily output is explicit, non-repeating calendar requests. A later native adapter must not translate Android calendar requests to absolute Expo DATE requests and claim equivalent timezone behavior.

Android eligibility requires a proven native calendar rearm capability that covers boot, clock and timezone events with the app closed. Absolute discretionary requests additionally require exact timing, a native fire-time state check and hard expiration. These capabilities are false until the real bridge is built and verified. iOS calendar availability does not imply discretionary expiration/recheck support. Unsupported dangerous scheduling produces no request.

Only current-day discretionary requests carry streak, recovery or freeze motivation. Their expiry is the local-day boundary (or the earlier actual recovery deadline), and no payload contains an hour/countdown figure. Future daily requests use evergreen habit copy. A future queue reservation rotates its copy locally within the plan; it is not persisted as delivered history. `NotificationDelivery` records only actual presentation and an optional actual completion within the declared two-hour reward window. Suppressed or merely queued entries must never count as use or reward.

The native reconciliation host must serialize replacements, debounce edits by `NOTIFICATION_CONFIG.rearmDebounceMs`, cancel prior owned requests before adding the complete desired set, and dismiss delivered notifications when their channel is disabled or their motivating state resolves. It must reserve room for unrelated pending requests via `otherPendingCount`; the planner also enforces the iOS ceiling and per-day budget. A stored pending request is not proof that the OS presented it. Presentation receives a fresh durable history/day/course/channel snapshot and the bounded session checkpoint lease. The native bridge must enforce expiration even when JS cannot run; otherwise its expiration capability stays false.

Tap handling must validate the installed course, await switching/parking that course, and only then route to the matching content. App/SQLite integration and native cancel/dismiss/rearm/tap behavior are not implemented by this pure checkpoint. Its test evidence is core behavior, not native delivery or a phase-green claim.
